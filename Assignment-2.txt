Azure App Service, Azure AD and AWS IAM vs Azure AD RBAC

Deploy a Sample Application to an Azure App Service Deployment Slot

First, I logged in to the Microsoft Azure Portal and searched for App Services.

I selected Create to start creating a new App Service. I selected the required subscription and resource group and then provided a suitable name for the web application.

For the runtime stack, I selected the one required by the sample application, such as .NET, Node.js, or Python. I also selected an appropriate region and App Service plan based on the requirements of the application.

After checking the configuration, I created the App Service and waited for the deployment to complete.

Once the App Service was created successfully, I opened it from the App Services list and went to the Deployment slots section.

I selected Add Slot to create a separate environment for testing. I named the new slot staging and used the production environment as the base for the slot.

After creating the staging slot, I opened it and deployed the sample application to the staging environment.

Once the deployment was completed, I opened the URL of the staging slot and checked whether the application was running correctly.

I verified that the application was accessible through the staging URL and that the production application was not affected by the changes made in the staging environment.

Finally, I checked the App Service, deployment slot, and running application and took screenshots for the assignment.

Register the Application in Azure AD

First, I opened Microsoft Entra ID from the Azure Portal. Azure AD is now known as Microsoft Entra ID.

From the left-side menu, I selected App registrations and clicked on New registration.

I entered a suitable name for the application, such as Sample-App-Registration.

Next, I selected the appropriate account type based on the requirements of the application. If the sample application required it, I also provided the redirect URI.

After checking the details, I clicked Register to create the application registration.

Once the registration was completed, Microsoft Entra ID generated an Application (client) ID and a Directory (tenant) ID. These IDs are used to identify the application and the Microsoft Entra tenant when connecting the application with Azure's identity and authentication services.

I noted these IDs and then checked the Authentication settings. I configured any additional authentication settings required by the sample application.

Finally, I verified that the application registration was created successfully and took a screenshot of the application registration page for the assignment.

AWS IAM vs Azure AD RBAC Comparison

For the third part, I reviewed the basic purpose of AWS IAM and Azure role-based access control.

AWS IAM, or Identity and Access Management, is used to control who can access AWS resources and what actions they are allowed to perform. Permissions are mainly defined using IAM policies and can be associated with users, groups, and roles.

In Azure, access to resources is commonly managed using Azure RBAC, which stands for Role-Based Access Control. It allows permissions to be assigned to users, groups, service principals, and managed identities through predefined or custom roles.

I compared how permissions are created and assigned in both platforms.

One of the main differences I found is that AWS IAM mainly uses policies written in JSON to define permissions, while Azure RBAC uses role definitions that specify what actions a user or identity can perform on Azure resources.

I also compared how users, groups, roles, and resources are managed in both cloud platforms.

AWS IAM is primarily focused on identity and permission management across AWS services, while Azure RBAC is closely integrated with Azure resources and uses role assignments at different scopes, such as a management group, subscription, resource group, or individual resource.
